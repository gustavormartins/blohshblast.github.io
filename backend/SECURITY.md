# API Security Model\n\n## Authentication\n- Email/password accounts use Node's built-in scrypt password hashing.\n- Access tokens are short-lived JWTs (15 minutes) signed with an environment-only secret.\n- JWT verification enforces HS256, issuer, audience, expiration, subject, and role.\n\n## Authorization\n- Mutating game endpoints require a bearer token.\n- Users can only submit scores for runs owned by their own user ID.\n- Admin resources require the `admin` role.\n- No role is accepted from request bodies.\n\n## Abuse controls\n- Per-IP global rate limit.\n- Stricter registration/login limits.\n- Per-user run and score limits.\n- Request body cap: 64 KiB.\n- Strict CORS allowlist.\n- No cookie authentication, so CSRF is not the authentication mechanism.\n\n## Validation\nAll JSON input is validated with Zod before database access. SQL queries use PostgreSQL parameters rather than string interpolation.\n\nScores additionally pass a server-side integrity envelope and must reference an active server-issued run owned by the caller.\n\nThe integrity envelope is an anti-abuse control, not a complete anti-cheat replay engine. A future authoritative replay protocol should validate the full move sequence against the server-issued seed and rules version.\n\n## Database\n- Credentials are supplied through Render's `fromDatabase` secret wiring.\n- No database credentials are committed to Git.\n- Migrations run before the API starts.\n- Foreign keys and database CHECK constraints provide a second validation boundary.\n- Production connections use TLS at the database layer.\n\n## Rate limiting scaling\nThe current limiter is in-memory and appropriate for the initial single-instance API. Before horizontal scaling, move rate-limit state to Render Key Value/Redis so all instances share limits.\n
